# Webhooks de eventos assíncronos

Status: proposta, aguardando aprovação. Data: 2026-11-15.

## Intenção

O usuário emite documentos de forma assíncrona (outbox → SNS → worker → SEFAZ). Hoje só descobre o resultado
pela tela (WebSocket) ou consultando a API. Webhooks avisam o sistema dele quando o resultado sai, sem polling.

Fluxo, igual ao do ctech-billing: o usuário cadastra uma URL; o DF-e prova que ela responde a um desafio antes de
ativar; depois de ativa, cada evento é entregue assinado, com log de cada tentativa; endpoint que falha demais é
desativado sozinho; uma entrega pode ser reenviada.

## Objetivos

- Cadastro com validação por desafio (`hub.challenge`) antes de ativar.
- Entrega assinada (HMAC-SHA256 sobre `timestamp.body`), com retentativas e backoff.
- Log de cada tentativa (status, duração, resposta truncada), 90 dias.
- Desativação automática após 12 falhas seguidas; reativação manual.
- Reenvio (replay) de uma entrega específica.
- Evento `ping` para testar um endpoint.
- Código de entrega, assinatura, desafio e anti-SSRF compartilhado em `go-common`; billing passa a usá-lo.

## Não objetivos

- Corpo com dados do documento além do mínimo (abaixo). Quem precisa do resto consulta a API.
- Entrega garantida exatamente uma vez: é pelo menos uma vez; o receptor deduplica pelo `id` do evento.
- Webhook por usuário: o escopo é a organização (filtro opcional por empresa).
- Eventos de cadastro (empresa, produto etc.): só eventos de documento fiscal.

## Anti-objetivos (falha mesmo que "funcione")

- Vazar dado fiscal numa URL errada: o corpo é mínimo por decisão.
- Fan-out dentro do caminho de escrita do resultado: um webhook quebrado não pode atrasar nem falhar o processamento do documento.
- Chamar IP privado/interno a partir do cadastro de um usuário (SSRF).
- Fila eterna de entregas que nunca vão passar (por isso a desativação automática).

## Corpo do evento (decidido)

```json
{
  "id": "evt_...",
  "type": "document.authorized",
  "occurred_at": "2026-11-15T12:00:00Z",
  "data": {
    "id": "<id do documento>",
    "access_key": "<chave de acesso, quando houver>",
    "status": "authorized",
    "rejection": {"code": "225", "message": "..."}
  }
}
```

`rejection` só existe quando `status` é `rejected`. Sem valores, sem destinatário, sem itens.
Cabeçalhos: `X-Ctech-Signature: v1=<hex>`, `X-Ctech-Timestamp`, `X-Ctech-Event-Id`.

Tipos da v1 (os mesmos estados terminais que o `ResultsConsumer` já recebe): `document.authorized`,
`document.rejected`, `document.failed`; mais `ping`.

## Abordagem (escolhida: C)

Três caminhos foram considerados para o código compartilhado:

- A. Motor completo com DynamoDB no go-common: obriga o billing a mudar o layout das tabelas. Descartado, risco alto.
- B. Só peças sem estado (assinatura, desafio, SSRF, regras): deixa a lógica de entrega duplicada. Descartado.
- **C. Peças + `Deliverer` genérico sobre uma interface `Store` pequena.** Escolhida: a lógica sensível
  (fan-out, backoff, desativação, concorrência por endpoint, replay) é uma só; o DynamoDB fica em cada serviço.

### go-common: pacote `webhooks`

- `Sign`/`Verify(secret, timestamp, body)`, tolerância de relógio no `Verify`.
- `Verifier` (desafio) com cliente guardado.
- `NewGuardedClient()` (recusa IP não público depois do DNS, sem redirect, sem proxy) e `PublicAddr`.
- `MaxFailureRun = 12`, `MaxDeliveryAttempts = 8`, backoff e `Deliverer` com `Store`:
  `DueDeliveries`, `GetEndpoint`, `RecordAttempt`, `MarkDelivered`, `MarkAttemptFailed`, `Defer`, `Close`,
  `RecordHealth` e `Requeue`; `Redeliver` faz o replay. O fan-out (qual evento vai para qual endpoint) fica em
  cada serviço, porque depende do domínio; o prefixo dos cabeçalhos é configurável (billing mantém `X-Billing-`).
  Plano de implementação: `docs/plans/2026-11-15-webhooks.md`.
- Origem do código: `ctech-billing/api/internal/services/delivering.go`, `webhook_verifier.go` e
  `domain/billing/webhook.go`. Os testes do billing viajam junto.

## DF-e: design (minhas decisões, ajustáveis)

- **Escopo:** organização; filtros opcionais por empresa e por tipo de evento (vazio = tudo).
- **Origem do evento:** o `ResultsConsumer` (api), ao receber um resultado terminal, grava o evento e as entregas
  pendentes numa transação. Nenhuma chamada HTTP no consumer.
- **Quem entrega:** Lambda `webhook-deliverer` agendada (EventBridge, 1 min) que lê um GSI esparso `due-index`
  (só entregas pendentes). Segue o padrão do `distribution-dispatcher`. Custo: poucas leituras por minuto, sem
  recurso sempre ligado novo.
- **Tabelas:** uma tabela `webhooks` (endpoints, eventos, entregas, tentativas; chaves por prefixo, como o billing),
  TTL de 90 dias em eventos/entregas/tentativas. Definida em `cdk/` (o CDK do DF-e não está congelado).
- **API:** `POST/GET/DELETE /v1.0/webhooks`, `POST /webhooks/{id}/ping`, `POST /webhooks/{id}/rotate-secret`,
  `GET /webhooks/{id}/deliveries`, `POST /webhooks/{id}/deliveries/{event_id}/replay`. Só owner/admin da organização
  cadastra e reenvia. Erros RFC 7807 via `problem`.
- **Segredo:** gerado pelo servidor (≥ 32 caracteres), mostrado uma vez, selado em repouso.
- **Limite:** no máximo 5 endpoints por organização (constante nomeada).
- **UI:** página `/webhooks` (lista, cadastro, ping, entregas, replay), registrada em `nav.tsx`, com seção e captura
  no guia (`/guide`).
- **Alertas:** desativação automática vai ao tópico SNS compartilhado via `alerts` do go-common.

## Resiliência (decisões)

- Timeout 10 s por tentativa; sem proxy; 3xx conta como falha.
- Retentativa com backoff; 12 falhas seguidas desativam; entregas de endpoint desativado saem da frente da fila.
- Se o DynamoDB do evento falhar no consumer, o resultado volta para a fila (comportamento atual do consumer);
  o webhook nunca bloqueia o resultado.

## Testes

Unit (assinatura, desafio, SSRF, backoff, regra das 12 falhas) no go-common; integração do `Store` no billing e
no DF-e (cadastro, desafio, entrega, falha, desativação, replay); UI: vitest e lint.
