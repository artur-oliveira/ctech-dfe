# Web Push Notifications na família CTech (piloto: DF-e)

Status: F1 (go-common `webpush` v1.43.0) e F2 (`@aoctech/push-client`) entregues; F3 (backend do DF-e) implementada e inerte até o operador gravar as chaves VAPID (ver `DEPLOYMENT.md`); F0 (teste manual nos aparelhos) e F4 (UI) abertas. Data: 2026-11-17.

## 1. Intenção

Hoje o DF-e avisa o resultado de uma emissão de três jeitos: tela aberta (WebSocket, `ResultsConsumer` →
`ws.Registry.Broadcast`), consulta à API e webhooks para sistemas (`docs/specs/2026-11-15-webhooks.md`). Falta o caso
mais comum de uma pessoa: ela emitiu, fechou a aba ou bloqueou o celular, e quer saber que a nota foi rejeitada, ou que
chegou um documento contra a empresa dela pela distribuição. Web Push (RFC 8030) resolve isso sem app nativo, em
Chrome/Edge/Firefox/Samsung no desktop e no Android, Safari no macOS e no iOS 16.4+ (só com o app instalado na Tela de
Início).

O DF-e é o piloto; o desenho vale para a família (account, wallet, billing, poker etc.) e por isso o código reutilizável
nasce em pacotes compartilhados.

## 3. Objetivos, não objetivos, anti-objetivos

Objetivos:
- Push no navegador/celular para: documento autorizado, rejeitado, com falha; documento recebido pela distribuição.
- Opt-in explícito com gesto do usuário, por dispositivo; preferências por usuário, por empresa e por evento.
- Implementação própria em Go com stdlib (RFC 8030, 8291, 8292), sem biblioteca de push de terceiros.
- Peças reutilizáveis na família: `go-common/webpush` e `@aoctech/push-client`.
- O app vira PWA instalável (necessário para iOS), sem cache offline.

Não objetivos (v1):
- Modo offline / cache de assets no service worker.
- Push para eventos de cadastro, billing, convites.
- Central de notificações dentro do app (histórico): a lista de documentos já é o histórico.
- Entrega garantida: push é melhor esforço com TTL; a verdade continua na tela e na API.

Anti-objetivos (falha mesmo que "funcione"):
- Dado fiscal ou pessoal na tela de bloqueio (valor, destinatário, CNPJ, nome do emitente, motivo da rejeição).
- Push bloqueando ou atrasando o `ResultsConsumer`.
- Pedir permissão de notificação sem gesto do usuário ou na primeira visita.
- Service worker servindo bundle velho.
- Enviar POST para uma URL arbitrária fornecida pelo cliente (SSRF via `endpoint`).

## 4. Decisão 1: chaves VAPID

### Como a inscrição se liga à chave

`pushManager.subscribe({userVisibleOnly: true, applicationServerKey})` amarra a inscrição à chave pública VAPID. O
serviço de push (FCM, Mozilla autopush, Apple, WNS) passa a exigir em cada envio um JWT ES256 assinado pela chave
privada correspondente (RFC 8292); com outra chave a resposta é 401/403. A inscrição também pertence a uma **origem +
escopo de service worker**: `https://dfe.aoctech.app/` e `https://accounts.aoctech.app/` geram inscrições diferentes
mesmo no mesmo navegador e com a mesma chave. Cada ambiente (`dfe-dev`, `dfe-stage`, `dfe`) é outra origem.

### Decisão: um par por serviço (frontend) e por ambiente

| Critério | Par único na família | Um par por serviço/ambiente (escolhido) |
|---|---|---|
| Reuso de inscrição entre produtos | nenhum: origens diferentes inscrevem de novo de qualquer forma | igual |
| Blast radius de vazamento | todo serviço guarda a privada; vazar uma vaza todas; com um endpoint vazado de outro produto, qualquer serviço comprometido envia push em nome de todos | só o produto afetado |
| Rotação | obriga todos os produtos a reinscrever ao mesmo tempo | independente, no ritmo de cada produto |
| Dev/stage tocando prod | possível se a chave for a mesma | impossível |
| Custo | zero | zero (parâmetros SSM Standard são gratuitos) |

Não existe ganho técnico no par único, só acoplamento e raio de dano maior.

### Onde guardar

SSM Parameter Store, padrão do repo (Secrets Manager cobra US$ 0,40/segredo/mês e não é usado no DF-e):

| Parâmetro | Tipo | Quem lê |
|---|---|---|
| `/ctech-dfe/{env}/push/vapid-private-key` | SecureString (PEM EC P-256, `openssl ecparam -name prime256v1 -genkey -noout`) | só a Lambda `push-sender` |
| `/ctech-dfe/{env}/push/vapid-public-key` | String (base64url do ponto não comprimido, 65 bytes) | API via `setup-ssm-env.sh` → `PUSH_VAPID_PUBLIC_KEY` |
| `/ctech-dfe/{env}/push/vapid-private-key-previous` | SecureString, opcional | `push-sender`, só durante a rotação |

A API nunca tem a privada (só serve a pública ao navegador). A `push-sender` confere no cold start que a pública
derivada da privada é igual ao parâmetro público e falha a subida se não for. O `sub` do JWT é a URL do app
(`/ctech-dfe/{env}/app-url`, já existe), que a RFC 8292 aceita e a Apple exige em formato `https:` ou `mailto:`.
Em outros serviços o caminho segue a mesma forma: `/ctech-{produto}/{env}/push/...`.

### Rotação

1. Gerar par novo; mover a privada atual para `...-previous`; gravar a nova e a pública nova.
2. Cada inscrição guarda `vapid_kid` (primeiros 8 bytes base64url de `sha256(chave pública)`). A `push-sender` escolhe a
   chave pelo `kid`; inscrição com `kid` sem chave carregada é apagada no envio.
3. O cliente compara `subscription.options.applicationServerKey` com a pública de `GET /push/config` a cada abertura
   do app; se diferir, `unsubscribe()` + `subscribe()` com a nova e `PUT` no servidor. Em Chrome/Firefox isso não pede
   gesto quando a permissão já é `granted`; no Safari/iOS pode exigir (risco R3), e a tela mostra "Reativar neste
   dispositivo".
4. Depois de 30 dias (`PushKeyGracePeriod`) remover `...-previous`. Rotação programada: só em suspeita de vazamento.

## 5. Decisão 2: onde moram inscrição e envio

| | A. Serviço central no ctech-account | B. Biblioteca go-common + tabela por serviço (escolhida) |
|---|---|---|
| Acoplamento | todo produto depende do account no caminho de cada notificação (M2M, breaker, fallback) | nenhum serviço novo no caminho |
| Disponibilidade | account fora = ninguém recebe push | falha fica contida no produto |
| Chaves | account guarda a privada de todos os produtos (ou volta ao par único) | cada produto guarda só a sua |
| Preferências | eventos são de domínio (NF-e rejeitada, saque, mão de pôquer); account teria de conhecer todos ou receber payload pronto | ficam no domínio, como o fan-out dos webhooks |
| Inscrição | continua por origem; account só centraliza armazenamento | igual, sem intermediário |
| Custo | chamada M2M por evento + tabela no account + tela de dispositivos no account | uma tabela on-demand por produto (centavos) |
| Ganho do central | uma tela única de "meus dispositivos" | perde isso (aceitável) |

Recomendação: **B**, a mesma abordagem C dos webhooks (peças sem estado e regras no go-common; DynamoDB e fan-out em
cada serviço). Revisitar só se três ou mais produtos adotarem e pedirem uma tela única de dispositivos no account; mesmo
assim seria uma listagem agregada, não o envio.

### go-common: pacote `webpush` (minor novo, `v1.43.0`)

Sem estado e sem DynamoDB. Superfície proposta:

```go
package webpush // gopkg.aoctech.app/api-commons/webpush

const (
    MaxPlaintext   = 3993            // RFC 8291 §4: corpo cifrado de um registro <= 4096 octetos
    RecordSize     = 4096
    DefaultTimeout = 10 * time.Second
    MaxEndpointLen = 2048
)

type Urgency string // "very-low" | "low" | "normal" | "high" (RFC 8030 §5.3)

type Subscription struct {
    Endpoint     string
    P256dh, Auth []byte // 65 e 16 bytes, validados
}

// ParseSubscription valida https, host na AllowedHosts, tamanho do endpoint,
// p256dh como ponto P-256 válido (ecdh.P256().NewPublicKey) e auth com 16 bytes.
func ParseSubscription(endpoint, p256dh, auth string) (Subscription, error)

type Key struct { // um par VAPID
    Private *ecdsa.PrivateKey
    Public  []byte // 65 bytes
    KID     string
}
func ParseKey(pem string) (Key, error)

// Encrypt aplica RFC 8291 (aes128gcm, RFC 8188) com chave efêmera e salt aleatórios.
func Encrypt(sub Subscription, plaintext []byte) ([]byte, error)

// VAPID monta "vapid t=<jwt>, k=<pub>" (RFC 8292) para a origem do endpoint.
func VAPID(k Key, endpoint, subject string, now time.Time) (string, error)

type Message struct {
    Payload []byte        // <= MaxPlaintext; o produto usa um teto menor
    TTL     time.Duration // obrigatório
    Urgency Urgency
    Topic   string        // <= 32 caracteres base64url, opcional
}

type Outcome int // Delivered, Gone, PayloadTooLarge, Unauthorized, Throttled, Rejected, Transient

type Result struct {
    Status     int
    Outcome    Outcome
    RetryAfter time.Duration
}

type Sender struct{ /* client, keys por KID, subject, now */ }
func NewSender(client *http.Client, subject string, keys ...Key) *Sender
func NewClient() *http.Client // transporte guardado + resilient (abaixo)
func (s *Sender) Send(ctx context.Context, sub Subscription, kid string, m Message) (Result, error)

var AllowedHosts = []string{ // sufixos; https obrigatório
    "fcm.googleapis.com", "updates.push.services.mozilla.com",
    "push.apple.com", "notify.windows.com",
}
```

O guarda anti-SSRF reaproveita `webhooks.NewGuardedClient` (dial recusa IP não público, sem redirect, sem proxy); a
lista de hosts é a segunda barreira. Decidido: `webpush` importa `webhooks.NewGuardedClient` direto; não se cria
pacote `netguard`.

## 6. Decisão 3: biblioteca de service worker e cliente de inscrição

Decidido: pacote separado **`@aoctech/push-client`** (repo `ctech-push-client`), no mesmo molde do
`@aoctech/ws-client`: lógica de infraestrutura sem componente visual. Não é subpath do `@aoctech/ui` porque lá só entram componentes e tokens, e o arquivo
do service worker precisa ser copiado para a origem do app, o que não combina com um pacote de UI. O card visual de
permissão (estados abaixo) é genérico e vai para o `@aoctech/ui` como `NotificationPermissionCard` (só apresentação,
recebe estado e callbacks), conforme a regra de que componente genérico local é bug.

Conteúdo do pacote:
- `dist/sw.js`: service worker sem build, sem Workbox, **sem handler de `fetch` e sem Cache Storage**. O app copia para
  `public/sw.js` num script `prebuild` (`cp node_modules/@aoctech/push-client/dist/sw.js public/sw.js`), e um teste no
  app compara os bytes para não divergir.
- `registerServiceWorker()`: `navigator.serviceWorker.register('/sw.js', {scope: '/', updateViaCache: 'none'})`.
- `usePushSubscription({getConfig, save, remove})`: estados `unsupported | needs-install | default | denied |
  subscribed | error`; `subscribe()` (precisa ser chamado dentro de um handler de clique), `unsubscribe()`,
  `syncOnLoad()` (reinscreve se a chave mudou e faz `PUT` no máximo uma vez a cada 24 h por dispositivo; o carimbo fica
  em `localStorage`, conveniência por dispositivo).
- Helpers `isIOS()`, `isStandalone()` (`matchMedia('(display-mode: standalone)')` ou `navigator.standalone`).

### Contrato do payload (v1)

O payload segue o formato do **Declarative Web Push** do WebKit (Safari 18.4+/iOS 18.4+), para que a notificação
apareça mesmo se o service worker falhar nessas versões, e o nosso `sw.js` lê os mesmos campos nos outros navegadores:

```json
{
  "web_push": 8030,
  "notification": {
    "title": "NF-e rejeitada · <nome curto da empresa>",
    "body": "Toque para ver o motivo.",
    "navigate": "/nfe/detail?key=<chave>&org=<company_pk>",
    "tag": "document.rejected:<hash curto da empresa>",
    "lang": "pt-BR",
    "silent": false,
    "data": {"v": 1, "id": "<event_id>", "type": "document.rejected"}
  }
}
```

Regras: `navigate` é sempre caminho relativo da própria origem (começa com `/`, nunca `//`); o `sw.js` descarta
qualquer outra coisa e usa `/`. Teto do produto: 1 KB (`PushPayloadBudget`), muito abaixo de `MaxPlaintext`. O campo
`data.v` versiona o contrato. Um arquivo dourado `webpush/testdata/notification-v1.json` no go-common é copiado para o
`push-client` e testado dos dois lados. Aceitação de campos extras pelo modo declarativo do iOS é verificada no spike
(F0, R6).

### Comportamento do `sw.js`

- `push`: `event.waitUntil(showNotification(...))` **sempre**. Chrome exige notificação visível (`userVisibleOnly`) e o
  Safari revoga a inscrição depois de pushes silenciosos. Payload ilegível vira "Nova atualização no CTech". Se houver
  janela do app focada (`clients.matchAll`), usa `silent: true`: o toast do WebSocket já avisou.
- `notificationclick`: fecha; procura janela da origem; se achar, `focus()` + `postMessage({type:
  'ctech-push:navigate', url})` e o app roteia (troca de empresa incluída); senão `clients.openWindow(url)`.
- `install`: `skipWaiting()`; `activate`: `clients.claim()`. Seguro porque o SW não guarda nada: trocar de versão não
  quebra página aberta.
- `pushsubscriptionchange`: sem handler na v1. O SW não tem token (o access token vive só na memória da página), então
  quem conserta é o `syncOnLoad()` na próxima abertura e a limpeza por 404/410 no servidor.

### Versionamento e atualização

`sw.js` carrega `const SW_VERSION = '<versão do pacote>'`; qualquer byte diferente dispara a atualização. O navegador
revalida o script do SW ignorando o cache HTTP (`updateViaCache: 'none'`, e o Cloudflare já serve com `max-age=0`).
Semver do pacote: mudança de contrato do payload é major e exige `data.v` novo, com o `sw.js` aceitando `v` antigo por
uma versão.

## 7. Decisão 4: tornar o app PWA

Recomendação: **sim, PWA "fino"**: manifest completo + service worker só de push, sem cache. É o único caminho para push
no iPhone e cobre o máximo de dispositivos; com o SW sem `fetch` handler os malefícios relevantes desaparecem.

Benefícios reais:
- **iOS/iPadOS 16.4+:** Web Push só funciona com o site adicionado à Tela de Início e com manifest `display:
  standalone`. Sem PWA, nenhum iPhone recebe push.
- Instalação no Android (Chrome gera WebAPK), Chrome/Edge desktop e Safari macOS (Adicionar ao Dock): ícone próprio,
  janela sem barra, abre direto no app; o clique na notificação abre a janela instalada.
- No Android, desktop Chrome/Edge/Firefox e Safari macOS o push funciona **sem** instalar; a instalação é opcional.
- Custo zero de infra; o Chrome não exige mais handler de `fetch` para oferecer instalação.

Malefícios e como ficam:

| Risco | Situação no nosso desenho |
|---|---|
| SW com cache servindo bundle velho após deploy (o clássico do PWA) | **não existe**: sem `fetch` handler, toda requisição vai à rede como hoje; `/_next/static/*` continua com hash e `immutable` |
| SW travado numa versão antiga | `skipWaiting` + `clients.claim` + `updateViaCache: 'none'`; SW sem estado; botão de emergência: publicar `sw.js` que só faz `self.registration.unregister()` |
| Escopo | `/sw.js` na raiz com escopo `/`; as rotas do export estático (`html_handling: auto-trailing-slash`) não interferem em `.js` |
| Next 16 `output: 'export'` | nada a mudar no `next.config.ts`; arquivo em `public/` vai para `out/`; registro num `useEffect` de um provider cliente |
| CSP | `default-src 'self'` já cobre o worker da mesma origem; ícones da própria origem |
| Login OAuth no app instalado (iOS) | a ida ao `accounts.aoctech.app` abre fora do escopo e volta ao app; o app instalado no iOS tem armazenamento separado do Safari, então o usuário faz login de novo uma vez. Testar no spike (R5) |
| Mesma origem, várias contas no aparelho | logout apaga a inscrição deste dispositivo (seção 10) |
| Firefox desktop | push funciona; instalação de PWA não é o caminho padrão. Sem impacto |
| Manifest atual com `name` vazio | corrigir: `name: "CTech DF-e"`, `short_name: "DF-e"`, `id: "/"`, `start_url: "/dashboard"`, `scope: "/"`, ícone `maskable`, `theme_color` do tema |
| Prompt de instalação | Chrome/Edge: botão "Instalar app" com `beforeinstallprompt` na tela de notificações; iOS: instrução "Compartilhar → Adicionar à Tela de Início" (com captura no guia) |

## 8. Decisão 5: implementação própria em Go (stdlib)

### Cifra (RFC 8291 sobre RFC 8188 `aes128gcm`)

Tudo em `crypto/ecdh`, `crypto/hkdf` (stdlib desde Go 1.24), `crypto/hmac`, `crypto/aes`, `crypto/cipher`,
`crypto/rand`:

1. `as_private` efêmera (`ecdh.P256().GenerateKey`), `as_public` 65 bytes; `ecdh_secret = ECDH(as_private, ua_public)`.
2. `PRK_key = HKDF-Extract(salt=auth_secret, ikm=ecdh_secret)`;
   `IKM = HKDF-Expand(PRK_key, "WebPush: info" || 0x00 || ua_public || as_public, 32)`.
3. `salt` aleatório de 16 bytes; `PRK = HKDF-Extract(salt, IKM)`;
   `CEK = HKDF-Expand(PRK, "Content-Encoding: aes128gcm" || 0x00, 16)`;
   `NONCE = HKDF-Expand(PRK, "Content-Encoding: nonce" || 0x00, 12)`.
4. Registro único: `plaintext || 0x02` (delimitador do último registro), sem padding extra; AES-128-GCM.
5. Corpo: `salt(16) || rs(uint32 BE = 4096) || idlen(1 = 65) || as_public(65) || ciphertext`.

`Encrypt` público usa aleatoriedade; uma função interna `encrypt(sub, plaintext, asPrivate, salt)` recebe as duas
entradas para o teste com o vetor.

### VAPID (RFC 8292)

- Cabeçalho JWS `{"typ":"JWT","alg":"ES256"}`; claims `aud` = `scheme://host` do endpoint, `exp` = agora + 1 h,
  `sub` = URL do app.
- Assinatura ES256 em **`r || s` de 32 bytes cada** (não DER): `ecdsa.Sign` e preenchimento à esquerda; armadilha
  comum que os testes cobrem.
- `Authorization: vapid t=<jwt>, k=<base64url da pública>`. Assina a cada envio (dezenas de microssegundos); cache de
  JWT por audiência fica para quando o volume pedir (`ponytail:` no código).
- Chave lida de PEM com `x509.ParseECPrivateKey`/`ParsePKCS8PrivateKey`.

### Requisição

`POST endpoint`, cabeçalhos `TTL` (segundos, obrigatório), `Content-Encoding: aes128gcm`,
`Content-Type: application/octet-stream`, `Urgency`, `Topic` (quando houver), `Authorization`. Payload acima de
`MaxPlaintext` é erro antes da rede.

### Respostas

| Status | Outcome | Ação do chamador |
|---|---|---|
| 201, 200, 202 | `Delivered` | nada |
| 404, 410 | `Gone` | apagar a inscrição |
| 413 | `PayloadTooLarge` | bug nosso: log + alerta `push-payload-too-large`, sem retry |
| 401, 403 | `Unauthorized` | chave não confere com a inscrição: apagar a inscrição; se todas as tentativas de uma execução derem 401/403 (mínimo 3), alerta `push-vapid-rejected` (configuração quebrada) |
| 429 | `Throttled` | `Retry-After` <= 2 s é esperado dentro do `resilient`; acima disso descarta para essa inscrição e loga `push_throttled` (push é melhor esforço; ver R7) |
| 400 e outros 4xx | `Rejected` | log, sem retry |
| 5xx, timeout, erro de rede | `Transient` | retry pelo `resilient` |

### Timeouts, retry e breaker

`webpush.NewClient()` = `resilient.NewHTTPClient(WithBaseTransport(<transporte do NewGuardedClient>),
WithTimeout(10s), WithMaxAttempts(2), WithBreaker(por host))`. O `resilient` só repete POST com `Idempotency-Key`;
o `Sender` envia `Idempotency-Key = resilient.DeterministicKey(event_id, sub_hash)` (cabeçalho desconhecido, ignorado
pelos serviços de push) para habilitar exatamente uma repetição com jitter, sem loop próprio. Duplicata eventual é
absorvida no aparelho pelo mesmo `tag` (substitui a notificação). Breaker aberto num host (FCM fora) devolve
`ErrCircuitOpen` e o resto do lote daquele host é pulado na execução.

### Testes do pacote

- **Vetor do RFC 8291 (§5 e apêndice A):** com `auth_secret`, `ua_public`/`ua_private`, `as_private`/`as_public` e
  `salt` do RFC, `encrypt` produz exatamente o corpo do RFC para a mensagem "When I grow up, I want to be a watermelon".
  Os valores são copiados literalmente do texto do RFC para `testdata/rfc8291.json` (não reescrever de memória).
- Ida e volta: um decifrador de teste (lado do agente do usuário, com `ua_private`) abre o que `Encrypt` gerou, com
  tamanhos de 0, 1, 1024 e `MaxPlaintext` bytes; `MaxPlaintext + 1` falha.
- VAPID: verifica a assinatura com a pública (`ecdsa.Verify` sobre `r || s`), claims, formato do cabeçalho, `aud` de
  endpoints com porta e caminho.
- `ParseSubscription`: host fora da lista, `http:`, credenciais na URL, ponto inválido, `auth` com 15 bytes; fuzz.
- `Sender` contra `httptest` (com o guarda desligado só no teste): cada linha da tabela de respostas, timeout,
  `Retry-After`, breaker.
- `go test -race`, staticcheck e govulncheck do go-common.

## 9. Decisão 6: produção e custo

### Tabela `{prefix}_push` (DF-e, CDK em `cdk/lib/dynamodb-stack.ts`; o CDK do DF-e não está congelado)

On-demand com teto (`maxRead/WriteRequestUnits: 1000`, como `webhooks`), chave própria da AWS, TTL em `ttl`, PITR só em
prod, RETAIN fora de dev.

| Item | pk | sk | Atributos | TTL |
|---|---|---|---|---|
| Inscrição | `USER#{sub}` | `SUB#{sha256(endpoint)[:16] hex}` | `endpoint`, `p256dh`, `auth`, `vapid_kid`, `device` (rótulo grosso derivado do User-Agent: "Chrome no Android"), `created_at`, `last_seen_at` | `last_seen_at` + 60 dias (renovado pelo `syncOnLoad`) |
| Contador | `USER#{sub}` | `META#counts` | `subscriptions` | não |
| Preferência | `COMPANY#{company_pk}` | `USER#{sub}` | `events` (string set), `user_sub`, `updated_at` | não |
| Dedupe | `COMPANY#{company_pk}` | `EVENT#{dedupe_key}` | nenhum | 24 h |
| Janela de agrupamento | `COMPANY#{company_pk}` | `THROTTLE#{event_type}` | `until` | `until` + 1 h |

GSI esparso `user-index` (pk `user_sub`, sk `pk`, `KEYS_ONLY`): só linhas de preferência; serve à exclusão LGPD da
pessoa e à remoção de membro. Sem Scan em lugar nenhum.

Acessos: tela de preferências = `GetItem(COMPANY#c, USER#u)`; lista de dispositivos = `Query USER#u begins_with SUB#`
(<= 10 linhas); fan-out = `Query COMPANY#c begins_with USER#` com `Limit` e cursor (`MaxPushRecipientsPerPage = 100`);
envio = um `Query USER#u` por destinatário.

Limites (constantes nomeadas): `MaxPushSubscriptionsPerUser = 10` (o 11º dispositivo substitui o de `last_seen_at` mais
antigo, na mesma transação do contador); `PushPayloadBudget = 1024`; `MaxPushEndpointLen = 2048`.

Selagem: as colunas `endpoint`/`auth` **não** são seladas com `fieldcrypt`. Sem a chave privada VAPID o endpoint não
aceita envio (o serviço de push exige o JWT da chave da inscrição), a tabela já é cifrada em repouso e só dois papéis IAM
a leem. Selar exigiria mais um segredo na API sem reduzir risco real. Revisitar se a auditoria LGPD pedir.

### Eventos v1

| Tipo | Origem | Título / corpo (pt-BR, sem dado sensível) | Link | TTL / Urgency / Topic |
|---|---|---|---|---|
| `document.authorized` | resultado terminal | "NF-e autorizada" / "Toque para abrir o documento." | detalhe | 12 h / normal / `sha(empresa+tipo)` |
| `document.rejected` | idem | "NF-e rejeitada" / "Toque para ver o motivo." | detalhe | 24 h / high / idem |
| `document.failed` | idem | "Falha ao emitir NF-e" / "Toque para ver o que aconteceu." | detalhe | 24 h / high / idem |
| `distribution.received` | `new_distribution_*` | "Novos documentos recebidos" / "Há documentos emitidos contra a sua empresa." | lista de distribuições | 24 h / low / idem |

"NF-e" muda conforme `document_type` (NFC-e, CT-e, MDF-e, NFS-e). Todo título termina com ` · <nome curto da
empresa>` (decidido), para quem tem várias empresas saber de qual veio. Fonte: `Organization.Name`
(`repositories/organizations.go`; não existe campo de nome fantasia separado), truncado em `PushCompanyNameMax = 30`
caracteres com reticências. É o nome da própria empresa do usuário, aceito na tela de bloqueio por decisão do produto.
Os três primeiros tipos reaproveitam as constantes `WebhookEvent*`; `distribution.received` é novo. Nunca vão para o
payload: valor, emitente (`emit_name`), destinatário, CNPJ, número, motivo da SEFAZ. A chave de acesso aparece só em `navigate`, dentro do payload cifrado de ponta a ponta
(o serviço de push não lê) e que não é exibido.

Agrupamento: um push por empresa e tipo por janela (`PushResultWindow = 1 min`, `PushDistributionWindow = 15 min`),
via `PutItem` condicional na linha `THROTTLE#` (`attribute_not_exists(pk) OR until < :now`). O primeiro evento da janela
leva o link do documento; os seguintes são suprimidos (a tela e a lista mostram todos). `tag` e `Topic` iguais por
empresa e tipo fazem o aparelho e o serviço de push guardarem só o mais recente. Isso evita 500 notificações quando um
lote inteiro rejeita.

### Preferências e opt-in

- Por usuário **e por empresa** (o mesmo usuário pode querer push de uma empresa e não de outra). Padrão ao ativar
  (decidido): **só `distribution.received` ligado**; `authorized`, `rejected` e `failed` começam desligados e o usuário
  liga o que quiser (`authorized` ligado num PDV de NFC-e geraria uma notificação por venda).
- Dois passos separados: (1) "Ativar neste dispositivo" pede permissão dentro do clique e cria a inscrição; (2) as chaves
  por evento. Nunca pedir permissão no carregamento.
- Recebe **todo membro que ativou** aquele evento na empresa, não só quem emitiu o documento (decidido; a mensagem de
  resultado também não traz o emissor de forma confiável). Quem não ativou nunca recebe.
- Recebe quem tem preferência na empresa **e** ainda é membro: o fan-out confere cada destinatário com o mesmo
  `MembershipService.Get` do RBAC (com o cache existente); a remoção de membro também apaga a linha de preferência.

### Fluxo de envio

```
ResultsConsumer.dispatch
  └─ após settleBilling e emitWebhook: emitPush(ctx, msg, event, orgPK)
       PushService.Emit
         1. tipo terminal ou distribuição? senão sai
         2. Query COMPANY#{orgPK} USER# (pref que quer este tipo)  → vazio: sai (custo: 1 leitura)
         3. confere membro de cada destinatário
         4. PutItem condicional THROTTLE#  → janela ocupada: sai
         5. PutItem condicional EVENT#{dedupe}  → já existe: sai (redelivery)
         6. Lambda Invoke (InvocationType=Event) push-sender {event_id, type, company_pk, document_type,
            document_key, recipients[sub...]}
            falha no invoke: apaga EVENT# e THROTTLE# (melhor esforço) e devolve erro → mensagem fica na fila
```

`dedupe_key` = o mesmo hash `company|documento|status` do `WebhookService.Emit`; extrair um helper único em vez de
copiar. Distribuição usa `company|access_key|distribution`.

Lambda `push-sender` (`api/cmd/push-sender`, binário do módulo api como o `webhook-deliverer`; 128 MB arm64, timeout
30 s, concorrência reservada 5, async `retryAttempts: 2`, `maxEventAge` 1 h):
- Cold start: lê as chaves VAPID do SSM, valida a pública, monta `webpush.Sender`.
- Para cada destinatário, `Query USER#{sub} SUB#`, monta o payload, envia com 8 em paralelo.
- `Gone`/`Unauthorized` apagam a inscrição (e decrementam o contador).
- Devolve erro **só** em falha de trabalho (SSM ou DynamoDB indisponível), para o retry assíncrono; falha de um envio
  nunca falha a execução. Sem destino de falha: o evento carrega `sub` e chave do documento e não deve ir para e-mail;
  falha de trabalho alerta pelo `alerts` com texto sem dados.

### Resiliência

| Dependência | Timeout | Retry | Breaker | Fallback | Abre/fecha |
|---|---|---|---|---|---|
| DynamoDB no `Emit` (consumer) | SDK + contexto | redelivery da fila | n/a | nenhum | fecha: erro mantém a mensagem (idempotente pelo `EVENT#`) |
| Lambda Invoke (consumer) | SDK | redelivery da fila | n/a | apaga marcadores | fecha, igual acima |
| SSM no cold start | SDK | retry assíncrono da Lambda | n/a | nenhum | fecha: sem chave não envia |
| Serviço de push | 10 s | 1 repetição com jitter (5xx/rede) | por host | descarta | abre: push perdido não afeta documento |
| `GET /push/config` na UI | cliente axios 10 s | cliente padrão | n/a | tela mostra erro | abre: app funciona sem push |

### Segurança, LGPD e limites

- Base legal: consentimento (opt-in por dispositivo, revogável a qualquer momento na tela, no navegador ou no logout).
- Dado guardado: identificador do dispositivo (endpoint), chaves da inscrição e rótulo grosso do aparelho. Entra no
  `services/erasure_catalog.go`: exclusão da pessoa apaga `USER#{sub}` e as preferências via `user-index`; exclusão da
  organização apaga as partições `COMPANY#` das empresas. Se nenhum `ErasureScope` existente casar com as duas formas de
  chave, cria-se um escopo `ScopePush` com purga própria; o teste do catálogo exige a entrada.
- Payload cifrado de ponta a ponta (RFC 8291); o texto visível é genérico.
- Rate limit: as rotas usam o `middleware.RateLimit` existente; `POST /push/test` tem limite próprio de 1 por minuto
  por usuário (go-common `ratelimit`). O agrupamento por janela limita o volume de saída.
- Anti-SSRF: lista de hosts + cliente guardado.

### Observabilidade

Só logs estruturados (sem métrica custom, sem alarme): uma linha por envio com `event_id`, `sub_hash`, `push_host`,
`status`, `outcome`, `duration_ms`; uma linha de resumo por execução. Consultas prontas de Logs Insights no `DOCS.md`.
Alertas via go-common `alerts` (tópico `/ctech/{env}/alerts/topic-arn`): `push-vapid-rejected`,
`push-payload-too-large`, `push-sender-failed` (falha de trabalho).

Premissas para 10 mil usuários: 30% ativam, 2 dispositivos cada (6 mil inscrições); 300 mil resultados terminais/mês,
dos quais ~50 mil viram push depois de preferências e agrupamento.

### Escopos OAuth (contrato)

Preferência de push é pessoal: qualquer papel, inclusive viewer, pode ligar a sua. Por isso as rotas usam
`RequireMember()` e não `Require("update.x")` (o viewer só tem `list/get`). Mas a sessão do `ui/` é um token "scoped",
e tokens de API não devem mexer em push sem escopo. Mudanças, todas na mesma alteração:

1. `oauthresource/scope-manifest.json`: `dfe:notifications:read` ("Consultar preferências e dispositivos de
   notificação.") e `dfe:notifications:write` ("Ativar, desativar e configurar notificações no navegador."), `status:
   active`.
2. `middleware/scopes.go`: família `notifications` em `scopeFamilies` (o teste de contrato compara as duas listas) e
   um guarda `RequireMemberScope(scope)` = `RequireMember` + "se o token for scoped, exige o escopo". Se o teste exigir
   o recurso em `repositories/roles.go`, adicionar `notifications` com `get/list/update` em todos os papéis.
3. `ui/src/lib/auth/oauth.ts`: os dois escopos em `DFE_USER_SCOPES`. Sem isso a própria UI recebe 403.
4. Publicação e concessão (decidido): o manifesto é publicado pelo scope-publisher (client dedicado do ctech-account,
   job `publish-resource-scopes.yml` do deploy). **Só o client OAuth da UI do DF-e recebe os escopos novos**, antes de
   a UI subir. Chaves de API existentes **não** são alteradas; quem quiser adiciona o escopo na própria chave. O escopo
   `notifications` não entra no conjunto padrão de chaves de API novas. Consequência: uma chave de API scoped sem o
   escopo recebe 403 nas rotas `/push/*`, que é o comportamento desejado.

### UI (`ui/CLAUDE.md`)

- Página nova **`/notifications`** ("Notificações") registrada em `src/lib/navigation/nav.tsx` (grupo de configurações,
  todos os papéis, `keywords`: push, alerta, aviso, celular, notificação, avisos no navegador). Rota `noindex` como toda

- Conteúdo: `NotificationPermissionCard` (`@aoctech/ui`) com os estados `unsupported` (navegador sem suporte),

- `RealtimeProvider` (ou um provider irmão) registra o SW, chama `syncOnLoad()` e escuta `ctech-push:navigate`; o
  roteamento troca para a empresa do `org` do link depois de validar o vínculo (hoje não existe tratamento de `?org=`
  nas telas de detalhe; criar no provider).
- Logout (`AuthContext.logout`, área crítica): antes de revogar, `DELETE /push/subscriptions/{id}` deste dispositivo e

## 12. Riscos

- **R1** O nome curto da empresa aparece na tela de bloqueio (decisão do produto). Nome longo é truncado em 30
  caracteres; numa empresa de CPF (espaço pessoal) o nome é o da própria pessoa.
- **R2** Lote grande rejeitado: o agrupamento por janela mostra uma notificação; o usuário precisa abrir a lista.
- **R3** Rotação de chave no iOS pode exigir gesto para reinscrever; tratado com o estado "Reativar".
- **R4** Aparelho compartilhado: mitigado pela remoção no logout; não cobre quem fecha sem sair.
- **R5** Login OAuth dentro do PWA instalado no iOS (armazenamento separado, volta do `accounts`). Validar no spike.
- **R6** Campos extras no formato declarativo do iOS 18.4+; se recusados, `data` sai do payload e o SW reconstrói pelo
  `tag`.
- **R7** 429 acima de 2 s descarta o push. Aceitável no volume previsto; revisitar se aparecer nos logs.
- **R8** Cabeçalho `Idempotency-Key` enviado aos serviços de push só para habilitar a repetição do `resilient`; se algum
  serviço recusar, trocar por uma opção `WithRetryPost` no `resilient`.
- **R9** `pushsubscriptionchange` sem handler: inscrição trocada pelo navegador fica sem push até a próxima abertura.
- **R10** Com rejeição e falha desligadas por padrão, quem ativa push e não mexe nas chaves só recebe distribuição. A
  tela de notificações deixa as chaves visíveis logo após a ativação e o guia explica isso.
- **R11** Integrações que usam chave de API scoped e por acaso chamem `/push/*` passam a receber 403 até o cliente
  adicionar o escopo na chave (comportamento esperado; registrar em `INTEGRATION.md`).

## 13. Decisões do usuário (2026-11-17)

- Título mostra o nome curto da empresa.
- Resultado vai para todo membro que ativou o evento na empresa, não só para quem emitiu.
- Todos os eventos começam desligados, exceto `distribution.received`, que começa ligado.
- Escopos `dfe:notifications:*` publicados pelo scope-publisher; só o client da UI os recebe; chaves de API existentes
  não mudam e o escopo não entra no padrão de chaves novas.
- `@aoctech/push-client` é pacote separado, não subpath do `@aoctech/ui`.
- `webpush` importa `webhooks.NewGuardedClient`.
